# Profile-guided document editing

Baseline: `1e14b95` (`1.0.1`). Candidate: tag `1.0.2`. Source hashes, raw samples and per-stage GUI records are in `1.0.2-samples.json`. V8 profiles are `1.0.2-before.cpuprofile` and `1.0.2-after.cpuprofile`; import them into Chromium DevTools' JavaScript Profiler. Source URLs are normalized and neither profile contains note bodies.

## Evidence and scope

An initial debug CPU profile showed about 551 ms of sampled time under the editable diff's update listener, mainly in `Text.toString` / `sliceString`. The code flattened the full persistent CodeMirror document on each edit before storing a string in the save session. Repeating matched profiles confirmed this path dominated large-file scripted input. This was the reason to change the code; no Git safety read was removed.

`src/editor-document.js` now owns the native document and its on-demand string representation. The save session accepts native document changes, uses exact native `Text.eq` against saved text for dirty checks, and retains its existing save queue/conflict protection. A clean first edit shares the previous CodeMirror document as the saved baseline. Restored or externally updated baselines use the same native `Text` representation. The public draft's enumerable `text` property remains readable and JSON-serializable; saving or workspace serialization materializes its string once for that version. Shared views can receive the native document directly. This keeps the conversion policy outside the view and avoids adding dependencies, worker infrastructure or mutable Git caches.

The change does not eliminate string work needed to save or serialize, and it does not reduce native diff calculation or browser rendering costs. Startup still defers CodeMirror loading until an editor is opened. Memory usage was not benchmarked.

## Environment and fixture

Local Windows x64, Obsidian 1.15.0 / Electron 43.8.4 / Chrome 150.0.7871.250, embedded Node v24.22.1, Git 2.50.0.windows.1. Both builds use the same dependencies and focused test window/editor. One temporary repository has one base commit, no stashes, exactly 100 Staged-only and 100 Changed-only files. The four targets alternate small Markdown, large JSON, small JSON and large Markdown, including deep paths and duplicate basenames. Actual working sizes are 36 bytes / 3 lines, 1,633,791 bytes / 96,003 lines, 34 bytes / 2 lines and 1,284,898 bytes / 24,001 lines.

Input benchmarks disable autosave, folding, highlighting, timing logging and plugin background refresh. One round is discarded, then five batches of 30 insert transactions are measured per target, after a first edit has entered the dirty state. Settling/fixture setup/Git reads are outside the synchronous batch timer. CPU sampling and the large-document `toString` probe are enabled for the profiled comparison; their overhead is included in the numbers below. No hard timing threshold is used in CI.

## Native input and GUI switching

An additional test used Electron native `char` events, checked `isTrusted` and completed 720 keys per build (600 measured keys after warm-up). Each 30-key batch includes native event delivery, event-loop settling and rendering work; it is not per-key latency or physical paint. Edits are placed near the middle of each file. Sampling is off.

| Scenario | Native 30-key batch ms, median [min–max], before | After | Samples |
| --- | --- | --- | --- |
| Small Markdown | 615.5 [525.8–1003.8] | 508.2 [498.7–516.4] | 5 batches |
| 1.6 MB JSON | 713.1 [683.1–726.9] | 655.5 [605.8–1174.8] | 5 batches |
| Small JSON | 525.5 [516.3–554.5] | 534.2 [493.9–562.1] | 5 batches |

Improvements are smaller and noisier with native event/rendering overhead included; the JSON candidate has a high outlier. Do not extrapolate the synchronous batch reduction to universal GUI speed. The native candidate already uses lazy conversion and saved-document sharing, but predates the final direct-document synchronization cleanup (that cleanup is covered by the final profiled comparison and shared-view regression).

File switching was profiled separately using 40 measured trusted native GUI clicks per build after eight warm-up clicks, alternating the four targets in both Staged and Changed groups. Records separate input delay, queue, DOM readiness, post-render verification, completion and animation-frame callbacks. CPU sampling is on. Mode/index assertions pass. Staged is HEAD→index, Changed is index→working file; the latter retains live path/operation/index and post-render checks.

This is a switching regression observation, not a switching speedup. CPU samples show editor creation/layout and subprocess startup; wall-clock spans also include Git wait. Profiles do not justify removing validation or introducing another Git cache. Timings slightly higher with overlapping ranges are recorded rather than described as improvements. This work does not establish a 50 ms switch target. Startup latency, physical paint, long-task distribution and memory improvements were not measured.

## Reproduction

1. Use a disposable running vault named `note_test`, no unsaved diff drafts, and pause other Git plugins. Build/install `1.0.1` from the repository root. Use the candidate's test scripts for both builds.
2. Set `window.__vbEditorProbe = { materialize: true, cpu: true }`, then evaluate `tests/manual/editor-updates-ui.js` in the developer console or via the Obsidian CLI. Save its returned report and `window.__vbEditorProfile` as JSON. Delete both globals after exporting. Run separately from builds and other tests.
3. For native input, set `window.__vbEditorProbe = { nativeInput: true }` and repeat. It checks native trusted events; do not label its batch duration as per-key response time.
4. For native GUI switching, evaluate `tests/manual/staged-switch-ui.js`, then `tests/manual/profile-switch-ui.js`. Save the returned report and `window.__vbSwitchProfile`; delete the profile global. The driver checks trusted clicks, waits for the fixture's wrapped `openDiff` completion flag with a bounded timeout and always cleans up.
5. Install `1.0.2` and repeat the same sequence. Editor and switching fixtures temporarily replace the plugin's Git service with an isolated temporary repository, restore settings/repository state and remove their fixtures. Keep the test window available throughout.

## Correctness checks

112 automated tests passed. New deterministic tests cover zero eager conversions on dirty checks, one conversion per serialized version, undo to saved content, CRLF/BOM, edits during save, string callers, restored drafts, exact same-length changes, external conflicts and reload. No timing threshold is required for those tests.

141 Obsidian UI assertions passed: shared editor (10), mixed-size loading (41), chunk revert (24), highlighting (25), startup/restored workspace (17), navigation (24). These include direct native-document synchronization between two views, JSON draft serialization, no manual-draft disk write, manual/autosave, index preservation, undo, near/over-2-MB fallback, external-edit protection, late-request cleanup and startup laziness.
