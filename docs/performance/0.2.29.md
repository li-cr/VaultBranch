# Trusted GUI diff clicks and optional tuning records

Baseline: release 0.2.28, commit `bfaf109`. Candidate: 0.2.29, the commit containing this document. Measurements use CDP Input mouse press/release events on actual sidebar file buttons, verified with `event.isTrusted`; they do not substitute direct calls to `openDiff` for the measured clicks.

## Findings and implementation

There is no fixed 100 ms delay in the production file-switching path. A newly acquired editable session reads complete live versions before constructing its editor, then performs another required synchronization after rendering. In the baseline, each snapshot serializes Git status, path validation, disk reading and index lookup. Its single immutable-blob cache thrashes when alternating different staged blobs, adding a size query and blob read on each first snapshot. Warm alternating clicks therefore execute six Git subprocesses: two status queries, two index lookups and one size/blob pair. In the visible-window recheck, small editors took about 8 ms to construct, while preparing their session took most of the roughly 182–184 ms before DOM readiness.

The candidate starts the independent status, filesystem validation and index lookup together, awaits all results and validates repository operation/conflict state before exposing content. Path/symlink checks, UTF-8/size limits, disk reads and current index lookups remain live. It retains the post-render synchronization and all save/external-change checks.

The immutable blob cache now uses an LRU Map capped at eight hashes and 4 MiB of UTF-8 text payload. JavaScript heap use is not the same as UTF-8 payload size and was not measured. Cache keys are Git hashes; staging different content changes the hash and forces a fresh read. Concurrent fills of one hash do not double-count capacity. Mutable worktree/index snapshots are not cached. Warm alternating clicks use four subprocesses; cold misses still require blob validation/reading.

## Tuning setting

Under **Settings → VaultBranch → Other**, **Tuning: record operation timings** is off by default. It records diff opening from the real sidebar handler, including source/trusted event, event delivery delay, navigation queue, save-before-switch, Git commands, path validation, disk reading, editor construction, DOM readiness, post-render verification and navigation completion. Readonly comparisons also carry Git/editor timings. The trace is passed explicitly through the operation; background work without that trace is not attributed to the click. No async hooks, polling timers or per-click log writes are used.

`View records` opens a local report with copy and clear controls. Only the most recent 100 records are retained in memory. Records contain relative paths, sizes, timing stages and status, without file bodies, raw Git output or automatic upload. Disabling, clearing or unloading invalidates pending trace completions as well as existing records. The enabled preference can persist; the records do not enter settings or workspace drafts. Disabled logging allocates no log/trace and schedules no profiling frame callbacks.

`domReadyMs` means the complete page has been synchronously constructed. `completedMs` also includes required post-render synchronization and the rest of native navigation. `firstFrameMs` and `nextFrameMs` describe requestAnimationFrame callbacks after construction, not guaranteed physical display paint. Hidden windows explicitly report unavailable frame timing. Nested/parallel stage durations overlap and must not be summed as wall time. The logger measures only diff-opening operations; it is not a whole-app profiler.

## Reproduction and environment

Use a disposable, independent `note_test` vault. Install the baseline's three release assets and run `node scripts/benchmark-gui-diff.cjs <test-CDP-port> off`. Install the candidate and run the same command with `off`, then `on`. The driver uses built-in Node WebSocket support and loads `tests/manual/gui-timing-fixture.js`; no additional dependency is required. Do not run builds/tests concurrently with these collections.

Windows 10 build 19045, Obsidian 1.15.0, Electron 43.8.4, embedded Node 24.22.1 and Git 2.50.0.windows.1. Same warm application/OS caches. Autosave/highlighting are disabled and native unchanged folding enabled. The fixture suppresses automatic sidebar refresh scheduling while preserving actual file reads, Git subprocesses and editor synchronization. It restores methods/settings, removes its own staged entries and trashes fixtures after each run.

Each run alternates 29-byte / 4-line Markdown, 1,633,783-byte / 96,003-line JSON, 31-byte / 4-line JSON and 1,284,890-byte / 24,001-line Markdown. JSON paths include `large/deep/json/data.json` and `small/deep/json/data.json`; Markdown basenames also repeat across directories. The staged content has one working-copy replacement adding two bytes. One warm-up cycle is discarded, followed by five measured cycles: five opens per file/build/mode, 20 trusted clicks per collection. Timing starts in a capturing click listener and does not include the driver's polling waits. Optional candidate records start at the sidebar handler immediately afterward, so their times can differ slightly from the independent observer.

All five collections are retained in [0.2.29-gui-timings.json](0.2.29-gui-timings.json). Measured candidate code precedes the metadata bump and reports version 0.2.28. The initial baseline window was hidden and lacked frame callbacks; the baseline was therefore reinstalled and collected again in the visible test window for the primary comparison. Initial candidate-on and baseline attribution samples are retained, but are not mixed with the primary table. Optional report records omit the warm-up/API opening and retain only the 20 measured sidebar traces.

The baseline implements no tuning logger; any unknown `performanceLogging` preference retained from testing the candidate has no effect in that build.

The primary comparison supports reducing diff-loading work while retaining current-state verification. Logging-on medians were 3.6–5.5 ms higher for DOM readiness and 9.6–13.6 ms higher for completion in this sequential local comparison. Process scheduling and filesystem noise also vary between runs; these differences are not a universal fixed logger overhead. Keep logging off for normal use and enable it while reproducing a delay. The initial candidate-on collection also showed improved DOM/completion times compared with the baseline; its raw samples are included.

These are local warm GUI file-switch measurements with full reads, not startup, physical monitor latency or whole-app performance. They do not promise every file becomes visible within 100 ms. Cold cache, long-line stress, peak memory and Linux/macOS UI were not measured here. Size boundaries and external-change behavior are covered separately by correctness tests. Timings are not CI thresholds.

## Validation

97 local automated tests pass. New coverage checks alternating cached blobs with live disk/staging changes, LRU entry/payload limits, concurrent status/index lookup that still rejects repository operations, bounded records, cancellation/clearing, explicit concurrent traces, disabled behavior and separate frame/completion semantics. Existing Git integration tests cover paths, symlinks, encoding, binary/size limits, stash, conflicts, branch operations and readonly history.

17 focused timing UI assertions pass for preference persistence, disabled logging, Git/editor/final-verification spans, readonly comparisons, error status/recovery, copy/clear, private-body exclusion, records absent from workspace/settings and disabling during a pending load. The native setting row was also opened and clicked in the actual settings panel. Another 38 mixed-size diff-loading assertions and 17 startup/restore assertions pass, with zero captured runtime errors. Test files/index entries and clean editor sessions are removed afterward. No cross-file undo-history improvement is claimed.
